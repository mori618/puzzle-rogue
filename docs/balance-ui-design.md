## 0. 要約

1. トークンも二つ名も、効果の強さは単体の数値では決まらない。**「どの層に効くか」×「いま何を持っているか」×「その手番をどう組んだか」** の3つで決まる。したがって調整も表示も「単体の値」ではなく **「このビルド・この組み方での限界倍率」** を基準にする。
2. そのために、コンボ計算を純関数に切り出し、**ゲーム本体（内訳パネル含む）とバランスシミュレータで同じ関数を使う**。これが本設計の土台（§4）。
3. バランス上の主要な問題は2種類（§3）: 上位互換の逆転（上位側を引き上げて解消）と、終盤に届く手段が一部のアーキタイプに偏っていること。**強い札・強い組み合わせ（指数札、会心の常時化、二つ名の重ねがけ、売買ループなど）は弱めない**（§3.2）。
4. 二つ名は現状 **約66効果のうち実際に動くのは10個前後**、解放条件の統計は大半が未記録、図鑑画面はどこからも開けない（§5.1）。数値調整より先に仕様確定が必要。
5. UIは「層が見える」「条件が見える」「実際にいくら効いたかが見える」の3点を足す（§6）。ショップの購入前プレビュー・相性表示は対象外。
6. 目標カーブ（§1.4）は据え置く。終盤はトークン側（スケール枠）で届くように調整する。既存の指数札は弱めず、スケール枠の無いアーキタイプに足す形で揃える。
7. **調整の大原則: 出る杭は打たない。** 強い札・強い組み合わせは弱めず、弱い側・手段の無いビルドを引き上げて「いろんなビルドで強くなれる」状態を目指す。値を下げる調整はしない。直すのは、効果が未定義・未実装で式が成り立たないものだけ。例外として、仕組みを単純にするための B層・D層の統合（D1）で加算の極意の組み合わせが弱くなるのは受け入れる。

## 1. 現状のコンボ計算モデル

### 1.1 計算式（`handleTurnEnd` の実装どおり）

```
基礎コンボ数   = floor( (素コンボ tc + 加算 A) × 基礎倍 B )
最終倍率       = (1 + 倍率加算の合計 Σ) × 乗算 D
そのターンの獲得 = floor( 基礎コンボ数 × 最終倍率 )      ※通常モードは 2,147,483,647 で頭打ち
```

| 層 | 内部変数 | 説明文での書き方（現状） | 代表例 |
|---|---|---|---|
| **A 加算** | `bonus` | 「コンボ+N」 | 力の鼓動、脈動、五連の巧技、ムーブドロップ |
| **B 基礎倍** | `baseMultiplier` ほか | 「基礎コンボ数がN倍」 | 誓約、一筆書きの誓約、最後の輝き、形の共鳴系 |
| **Σ 倍率加算** | `addedMultiplier` | 「コンボ倍率にプラスN」 | 連舞、律動、真髄、極致、会心、厄災の祈り |
| **D 乗算** | `multMultiplier` | 「基礎コンボ数がN倍」 | 二重奏、四/六重奏、秘儀、禁忌、背水の陣、千手観音 |

補足（実装上の事実）:

- 画面の内訳表示は「基礎コンボ数 × コンボ倍率」の2項で、B と D はどちらも左側（基礎）に掛かる演出になっている。**プレイヤーから見える「つまみ」は3つ（＋加算 / ×基礎 / ＋倍率）**。
- ただし B と D は内部では別物で、次の2点で挙動が変わる。説明文はどちらも「基礎コンボ数がN倍」で区別できない。
  - **加算の極意**は Σ と D を無効化するが、**B は無効化しない**。 → D1 で B と D を「基礎倍」1種に統合し、極意は基礎倍すべてを無効化すると決定。
  - **犬神**（基礎100以上で×10）の判定は B 適用後・D 適用前の値で行う。 → 統合後は「加算後・基礎倍の前」で判定する（§7.4）。
- Σ系トークンの `values` は内部では「倍相当値」で、表示は −1 した値（連舞 `[2,3,4]` → 表示「+1/+2/+3」）。本書の数値は**表示値**で書く。
- 二つ名の Σ 効果は、加算の極意が Σ を 0 にリセットした**後**に足されている（=極意の制約をすり抜ける）。→ D5 で極意が二つ名の Σ も無効化すると決定。

### 1.2 層ごとの伸び方（組み合わせで価値が変わる理由）

同じ「+3」「×2」でも、手持ち次第で実質の効きが変わる。

| すでに持っている Σ 合計 | 新たに「+3」を足した時の実質倍率 | 「×2」を足した時 |
|---:|---:|---:|
| 0 | ×4.00 | ×2.00 |
| +3 | ×1.75 | ×2.00 |
| +6 | ×1.43 | ×2.00 |
| +12 | ×1.23 | ×2.00 |
| +20 | ×1.14 | ×2.00 |

- **Σ（倍率加算）は序盤最強・積むほど薄まる。× は常に一定。** 「+k」と「×m」の損益分岐は `Σ合計 = k/(m−1) − 1`。
- A（加算）も同じ構造で、素コンボ7に +15 は ×3.1 だが、すでに +100 あるなら ×1.14。
- つまりスロットが増える後半ほど × 系の価値が相対的に上がり、**Σ系トークンは「1〜2枚目」と「4枚目以降」で別物**になる。値付けはこの前提で行う。

### 1.3 パズルの組み方で変わる入力

各トークンの条件は、ターン結果の次の値を見ている。組み方を変えると、同じ盤面でもどの条件が点くかが変わる。

## 2. 評価方法：限界倍率マトリクス

### 2.1 指標

> **限界倍率** = （そのトークン/二つ名あり の獲得コンボ）÷（なし の獲得コンボ）
> を、**基準ビルド × 基準パズルパターン** の全組み合わせで計算したもの。

1つのトークンにつき次の3値を見る。

- **最適値**: いちばん噛み合うビルド×パターンでの限界倍率（＝天井）
- **汎用値**: 全組み合わせの中央値（＝何も考えずに入れた時の強さ）
- **成立率**: 条件が点く組み合わせの割合（＝組み方をどれだけ縛るか）

「最適値が高く成立率が低い」ものは **組み方を寄せる報酬** として健全。「汎用値が高い」ものも下げない。比較の指標として使う。

### 3.3 終盤の目標が「壊れ札」前提になっている

§1.4 の必要倍率に対し、突出札を除いた標準的な9枠ビルド（加算+15、Σ 計+18、× 3枚で×48、Lv3想定）の出力は **およそ 2万/手、一刃の極意を使った手で10万**（概算）。これはサイクル15（5.1万/手）前後で止まる水準。

- サイクル16以降（32万〜14億/手）は、T6〜T10、加算の極意、先導（効果2度発動）、模倣の魔鏡などの**突出札がないと届かない**。突出札があること自体は問題ではなく、**ハート寄せと汎用以外のアーキタイプには届く手段が無い**ことが問題。
- 9枠すべてをパッシブにしても、サイクル25到達には**1枠あたり平均 ×8.4** が必要（204M の9乗根）。バンド上限（★3 Lv3 で ×5）を超えている。

→ 突出札は弱めない。**§7.3 のとおり「スケール枠」を全アーキタイプに配る形で揃える**。

| 札 | 効果 | 評価 |
|---|---|---|
| 空の神 | 所持10個以下で ×4 | 通常モードの最大枠は9なので常に成立する。伝説として強いのは可。据え置き |
| 曲芸師 | ハート2コンボで ×7 | 同条件の二重奏 Lv3 が ×3。妥当な伝説 |

| 聖女 / キング / 覚醒 | 仕組みを変える系 | ビルドを選ぶ。数値比較の対象外 |

### 3.5 層の表記と実挙動のずれ

- 「基礎コンボ数がN倍」が B と D の両方に使われ、加算の極意・犬神との相性が説明文から判断できない（§1.1）。
- 加算の極意の説明は「コンボ倍率系の効果が一切発動しなくなる」だが、**B層（誓約・一筆書き・最後の輝き・形の共鳴系など約20種）は発動する**。→ D1・D2 で B も止めると決定（極意×B層の組は弱くなるが、仕組みの単純さを優先）。
- 四天/五色/六色の秘儀は `color_multiplier` 系だが D 層（×）、同系統の連舞・律動は Σ 層。名前の系統と層が一致していない。

### 3.6 価格

- パッシブの中央値は ★1: 15 / ★2: 20 / ★3: 28 / ★4: 77。同カテゴリ所持1個ごとに ×1.15。
- 価格が強さを反映していない例: 交差する秘技 30★ など（生命の器・千手観音は突出枠として価格も据え置き）。
- 価格は §2 の最適値で引き直す（§7.5）。

### 3.7 仕様書とのずれ

## 4. 基盤：計算の純関数化とシミュレータ

### 4.1 `calcTurnResult` の切り出し

`handleTurnEnd` の中にある計算部（現状 約1,500行、React state と演出呼び出しが混在）を純関数にする。

```
// src/engine/comboCalculator.js
calcTurnResult({
  turnInput,     // §1.3 の入力（素コンボ、色別、形、落ちコン、残り時間、特殊消去数…）
  tokens,        // 有効トークン（コピー・先導の展開後）
  titleEffects,  // 装備中の二つ名効果
  runState,      // stars, turn, maxTurns, currentRunStats, activeBuffs
  rng,           // 確率系用。シミュレータでは期待値モード/固定シードを渡す
}) => {
  base, bonus, baseMult, addedMult, multMult, final,
  steps: [{ sourceId, sourceType: 'token'|'title'|'system', layer: 'A'|'B'|'Σ'|'D',
            value, fired: true|false, reason }],
}
```

- 演出（`triggerPassive`、`notify`）は戻り値の `steps` を見て呼び出し側で行う。
- **不発だったトークンも `fired:false` と理由つきで返す**（UIの内訳で使う。§6.3）。
- 既存の `logData.bonusSteps / multiplierSteps` はこの `steps` に統合する。
- 既存テスト（`PuzzleEngine.comprehensive.test.jsx` など）に加え、切り出し前後で同じ入力に同じ結果が出るスナップショットテストを先に作ってから移行する。

### 4.2 バランスシミュレータ

`scripts/balance-sim.mjs`（`npm run balance`）:

1. §2.2 のパターンと §2.3 のビルドを JSON で読み込む。
2. 全トークン・全二つ名について、限界倍率（最適値 / 汎用値 / 成立率）を算出。
3. 二つ名は **A枠24 × B枠24 = 576通り**＋進化を総当たりし、B0・B3 の各段階で評価。
4. 出力: CSV（`scratch/` の既存バランスシートを置き換え）と、違反一覧（§2.4 のバンド下限割れ、上位互換の逆転）。売買ループは記録のみ。
5. 進行シミュレーション: 基準ビルドの「サイクル別 到達可否」を出し、§1.4 のカーブと重ねる。

実装メモ（ステップ2時点）:

- 型・脈動・落ちコン・加算の極意などの**連鎖中の加算**は `src/engine/realtimeBonuses.js` に切り出し、ゲーム本体（`PuzzleEngine`・`useGameState`）とシミュレータで共用する。パターンは消えたグループの一覧（`groups`）で定義し、素コンボはそこから計算する。
- 色指定のある札は、評価時に1色目を炎・2色目を月に寄せる（パターンを色ごとに用意しないため）。
- 札自身の効果が発動しなかった組では限界倍率を 1 とする（三星の極雷の「★3の所持数」などの相乗効果だけで上がった分を除くため）。
- 上位互換の逆転は「同じLvで、低レアの札が全ての組で同等以上」。代償のある札は代償のある札同士でだけ比べ、所持数の相乗効果で結果が決まるビルド（B10）は比較に使わない。
- 対象外: 二つ名（このブランチに未実装）、模倣・先導・試練によるトークン複製の連鎖中加算、ボム爆発分の加算。
- 現状値で §3 の T1（律動）・T2（極致）・T4（背水の陣）は逆転として検出される。T3（六重奏と誓約）は、誓約の代償をスキルで回避できるかという問題で、固定パターンでは測れない。

### 4.3 データ定義の拡張

各トークン定義に、UIと検証の両方で使うメタ情報を足す。

```js
{ id: "req_12_fire", ...,
  layer: "Σ",                               // A | B | Σ | D | board | economy | time | system
  cond: { colors: ["fire"], minErased: 12 }, // 条件の構造化（タグ表示・シナジー判定に使用）
  boostable: "value",                        // 増幅系の対象か: value | none | inverse（閾値系）
}
```

`SPECIFICATION.md` 附録とトークン図鑑は、この定義から生成する。

### 5.2 二つ名の役割定義（提案）

> **二つ名は「ランの前に選ぶ、組み方の方針」。** スロットを使わず常時効くので、強さではなく**方向づけ**で価値を出す。

- **A枠（接頭辞）= どう組むか**（条件・制約・盤面の偏り）
- **B枠（接尾辞）= 何が伸びるか**（増幅・経済・スキル）
- **セット = 特定の A×B にだけ出る「仕組みが変わる」効果**（数値の上乗せではなく挙動変化）
- **進化 = 元の方針を尖らせる**（代償も増える）

| 項目 | 決定 |
|---|---|
| 変更タイミング | **ラン開始時のみ**（`StartOptionScreen`）。ラン中は変更不可 |

### 5.6 デメリット重複ルール（トークン×二つ名、二つ名×二つ名）

同じ代償を持つ効果を重ねると、2つ目以降は代償なしで利得だけが乗る。

| 重複する代償 | 該当 |
|---|---|
| 落ちコン停止 | 禁忌の儀式（トークン）、禁忌の（A枠）、静寂の呪縛（呪い） |
| 操作時間固定 | 背水の陣（4秒）、背水の（4秒）、焦燥の刻印（4秒）、暴君の号令（2秒）、刹那の呪縛（1秒） |
| 操作時間減少 | 狂戦士の、修羅の、呪われた力 |

方針:
- **重複は「同じ方針に寄せた報酬」として許可する。** 値は下げない。
- **固定時間が複数ある場合は最小値を採用**する（現状は二つ名の「背水の」が最後に上書きし、暴君の号令の2秒固定を4秒に**緩和**してしまう）。
- 「固定」は加減算より後、最小保証（1秒）より前に適用する。順序: 基本 → 加減算 → 次手倍率 → 固定（最小値）→ 下限。

### 5.7 総当たりで監視する組み合わせ

シミュレータ（§4.2）で 576通りを機械的に検査するが、設計段階で特に注意する組:

| 組み合わせ | 懸念 |
|---|---|
| 増幅の × 探求者 × 加算の極意 | A層に 1.3×1.5×100。線形なので可だが、犬神（基礎100以上）が常時成立する |
| 孤高の × 無双 / 覇王 | 3枠ビルドに無条件効果が2つ乗る。序盤の素通し確認 |
| 属性接頭辞 × 統率者 | 同色寄せの二重取り。桁あふれしないかを確認 |
| 属性接頭辞 / 偏愛の × 二極化 × 誓約トークン | 対立色が降らなくなり、誓約の制約が消える |
| 禁忌の × 即応陣 | 落ちコン停止で盤面が完全に決定的になり、変換スキル満タンと合わせて毎サイクル確定手になる |

### 7.3 終盤の設計方針（§3.3 への対応）

### 7.5 価格の再設定

シミュレータの最適値（Lv1）から機械的に引く。初期式:

```
基準価格 = round( 10 × 最適値(Lv1)^2 × レア補正 )     レア補正: ★1=1.0 / ★2=1.1 / ★3=1.25
```

例: 最適値 1.3 → 17★、1.6 → 28★（★2）、2.0 → 50★（★3）。盤面・経済系は倍率で測れないため現行価格を基準に手で付ける。同カテゴリ所持による ×1.15 は据え置き。
