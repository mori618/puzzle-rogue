# Claude 依頼用プロンプト集（テストプレイログ分析 2026-11-02）

2026-11-01〜02 のテストプレイログ 9 ラン（重複除く）の分析結果と、開発者の追加案をまとめたもの。
似た内容ごとにグループ化してあるので、**1 グループ = 1 回の依頼**として、各「プロンプト」欄をそのまま Claude に貼り付けて使う。

## 分析の要点（共通の背景）

- 9 ラン中 8 ランがサイクル 6 で終了（目標 368 に対し最高 166 = 45%）。サイクル 1〜5（目標 8〜56）はほぼ毎回 1〜2 手でクリアし、残りはスキップしていた。
- 二つ名がサイクル 1〜5 のコンボを 2〜4 倍に押し上げており、トークンを育てなくても序盤を抜けられてしまう。一方、固定値の加算はサイクル 6 以降で伸びない。
- 死亡時にスターが平均 36（12〜84）余り、トークン枠の拡張は全ランで 0 回だった。
- 効いていたトークンは倍率系（月の真髄・常闇の共鳴・業水の律動・各色の連舞・重力逆転）。条件の重い発動型トークンは、サイクル 6 までにほぼ発動しなかった。

## 推奨する依頼順

1. グループ 1（目標値）
2. グループ 2（二つ名の切り替えとログ）
3. グループ 3（属性の福音トークン廃止と属性二つ名の強化）
4. グループ 4（二つ名の強さ調整）
5. グループ 5（発動型トークンと誤字）
6. グループ 6（変換の演出）

グループ 1〜5 はどれもバランスに関わるため、1 つ入れるごとにテストプレイしてから次へ進むのがよい。グループ 6 は見た目だけの変更なので、いつ入れてもよい。

## グループ 1：サイクル 6 の目標値を下げる（済）

**背景**：サイクル 5 → 6 で目標が 56 → 368（約 6.6 倍）に跳ね上がり、ほぼ全ランがここで止まっている。サイクル 11 の目標はほぼ「+5000」で決まるので、サイクル 6 を下げても後半への影響は小さい。

| 式 | C6 | C7 | C10 | C11 |
|---|---|---|---|---|
| 現在 ×3.0+200 | 368 | 588 | 2,406 | 14,624 |
| 変更後 ×3.0+60 | 228 | 364 | 1,489 | 10,956 |

**プロンプト**

```
サイクル6の目標値の跳ね上がりを緩めたいです。

- src/hooks/useGameState.js の startNextCycle 内、目標値の計算で
  `if (i === 6) { mult = 3.0; add = 200; }` を `mult = 3.0; add = 60;` に変更してください。
  （サイクル6の目標が 368 → 228 になります）
- 目標値を参照するテストがあれば更新してください。
- README.md と SPECIFICATION.md にある目標値の表（サイクル6以降の概算値）も、新しい計算結果に合わせて更新してください。
- npm test と npm run build が通ることを確認してください。
```

## グループ 2：二つ名の切り替えにスターを消費させ、切り替えをログに残す

**背景**：
- ゲーム中に二つ名を何度でも無条件で切り替えられるため、状況に応じて付け替えるのが最適解になってしまう（開発者案：切り替えにスター消費を必要にする）。
- 切り替えがプレイログに記録されていない。開始時の二つ名と実際の計算に出てくる二つ名が違うランが 3 本あり、うち 1 本はサイクル 3 以降に二つ名の効果が消えていたが、原因を追えなかった。

**プロンプト**

```
ゲーム中の二つ名切り替えについて、2点お願いします。

1. 切り替えにスターを消費するようにしてください
   - 現在はゲーム中（ラン中）に二つ名を無条件で何度でも切り替えられます
     （src/App.jsx の onChangeTitle 周辺、src/utils/titleManager.js）。
   - ラン中の切り替えに★を消費するようにしてください。価格案：初回 5★、
     同じラン内で切り替えるたびに +5★ ずつ上がる（5→10→15…）。
     ラン開始前（タイトル画面など）の装備変更は無料のままにしてください。
   - スターが足りないときは切り替えボタンを押せないようにし、
     必要なスター数を表示してください。
   - 切り替え価格はセーブデータに保存し、ロード後も引き継がれるようにしてください。
   - 価格の数値は定数にして、後から調整しやすくしてください
     （src/constants/gameConstants.js など）。

2. 切り替えをプレイログに記録してください
   - src/utils/playLogger.js の仕組みで、切り替えのたびに
     `titleChange` イベント（変更前後の A枠/B枠の id と名前、消費した★）を記録してください。
   - あわせて、記録時点の二つ名効果（meta.titleEffects と同じ形式）も残してください。
     現在の meta.titleEffects はラン開始時の値のままなので、
     途中で付け替えると実際の効果と食い違います。

テストを追加し、npm test と npm run build が通ることを確認してください。
```

## グループ 3：属性の福音トークンを廃止し、属性二つ名を強化する

**背景**：「炎の福音」など、ショップに特定属性のトークンを出やすくするトークン（`shop_attr_*`、効果 `shop_attribute_weight`、10★、×2/3/4）は弱く、枠を 1 つ使う価値がない。同じ効果（`shop_attr_weight` ×2）は属性の二つ名（紅蓮の／常月の など）にもあるので、トークンを廃止して二つ名側を少し強くする（開発者案）。

**プロンプト**

```
ショップの属性出現率を上げるトークンを廃止し、その役割を属性の二つ名に移したいです。

1. トークンの廃止
   - src/constants/tokens.js の「ショップ属性出現率アップ」セクションにある
     shop_attr_fire / water / wood / light / dark / heart / none
     （effect: "shop_attribute_weight"）をショップに出ないようにしてください。
   - 既存のセーブデータで所持している場合に壊れないよう、定義を消すか
     出現候補から外すだけにするかを判断して対応してください
     （所持中のものは売却できる・効果は残す、など安全な方で構いません）。
   - useShop.js の shop_attribute_weight 処理、図鑑、テスト
     （PuzzleEngine.comprehensive.test.jsx の effect 一覧など）も整合させてください。

2. 属性二つ名の強化（src/constants/titles.js の A04〜A09 など、
   shop_attr_weight を持つ二つ名）
   - shop_attr_weight を ×2 → ×3 にしてください。
   - spawn_weight を 1.25 → 1.35 にしてください。
   - desc の表記（「出やすくなる（2倍）」「少しUP」）も新しい値に合わせてください。
   - 多色系の二つ名に shop_attr_weight があれば、同じ方針で揃えてください。

テストを更新し、npm test と npm run build が通ることを確認してください。
```

## グループ 4：二つ名の強さを序盤偏重から直す（済）

**背景**（サイクル 1〜5 の平均で、二つ名あり／なしのコンボを比較）：

| 二つ名 | 二つ名なしの何倍か | 問題 |
|---|---|---|
| 狂戦士の＋覇王 | 約 4 倍 | 序盤に強すぎる |
| 疾風（4 マス移動ごとに +1、最大 +30） | 約 3〜4 倍 | 序盤の素のコンボ（5〜8）に対して +10〜14 は大きすぎる |
| 禁忌の（毎手 +8） | 約 2.2 倍 | 序盤は強いが伸びず、サイクル 6 では最下位（11%） |
| 覇王（倍率 +1.5） | 2.5 倍 | 解放条件（1 手で 5 万コンボ）の重さのわりに後半は物足りない |

固定値の加算は「序盤に強く、後半で腐る」ので、序盤を抑えて後半に伸びる形にしたい。

**プロンプト**

```
二つ名の強さが序盤に偏っているので調整したいです（src/constants/titles.js）。
テストプレイの分析では、サイクル1〜5で二つ名がコンボを2〜4倍に押し上げ、
トークンを育てなくても序盤を抜けられてしまう一方、
固定値の加算はサイクル6以降で伸びませんでした。

1. 疾風（B41）：最大を +30 → +12 に下げてください
   （effects の max: 120 → 48。desc も「最大+12」に）。
2. 固定値の加算を持つ二つ名（背水の A03 +6、狂戦士の A02 +5、禁忌の A12 +8 など、
   combo_add の固定値）を、サイクル数に比例して伸びる形にしてください。
   例：「毎手番コンボ +(サイクル数 × 1)」に、二つ名ごとの係数を掛ける
   （禁忌の ×1.5、背水の ×1.2、狂戦士の ×1.0 程度）。
   - combo_add に per: 'cycle' のような指定を追加し、効果を計算している箇所
     （src/utils/titleManager.js と useGameState.js のコンボ計算）で対応してください。
   - desc に計算式と現在値がわかる表記を入れてください。
3. 覇王（B01）：解放条件が1手5万コンボと重いので、序盤の倍率は据え置きか少し下げ、
   後半に伸びる要素を足す案を提示してください（実装前に案を見せてください）。

数値は定数として調整しやすくし、テストを追加・更新してください。
npm test と npm run build が通ることを確認してください。
```

## グループ 5：発動型トークンの条件を軽くし、名前の誤字を直す

**背景**：
- 「4 連の流星」「方陣の残響」「5 連 of 成長」は、サイクル 6 までにほぼ発動しなかった（1 回発動したかどうか）。条件の重さに対して効果が届くのが遅い。
- トークン名が「5 連 of 成長」になっている（`src/constants/tokens.js:4051`）。発動時の通知は「5 連の成長」。以前直した「方陣 of 輪廻」と同じ種類の誤字。

**プロンプト**

```
発動条件の重いトークンの調整と、名前の誤字修正をお願いします（src/constants/tokens.js）。

1. 誤字修正：len5_count_level_up の name が「5連 of 成長」になっているので
   「5連の成長」に直してください。他にも name や desc、通知文に
   「 of 」が混ざっているものがないか全体を検索し、あれば同様に直してください。

2. 発動条件の緩和
   - square_count_combo_mult（方陣の残響）：正方形消しの累計 3回ごと → 2回ごとに。
   - len5_count_level_up（5連の成長）：values [10, 8, 1] → [6, 5, 1] 程度に。

   - desc のプレースホルダ・表記も合わせて更新してください。

3. 同じように、累計カウントで発動するトークン（square_count, len5_count,

npm test と npm run build が通ることを確認してください。
```

## グループ 6：ドロップ変換の演出を追加する

**背景**（テストプレイのメモより）：ドロップが別の種類に変わる効果に演出がなく、急に変わったように見えて驚く。特に、ターン終了後に自動で変換される処理（`turn_end_convert` など）は、気づいたら盤面が変わっている感じがある。

**プロンプト**

```
ドロップが別の種類に変換されるときの演出を追加したいです。
今は一瞬で切り替わるため、特にターン終了後の自動変換が
「いきなり変わった」ように見えて驚きます。

対象：
- ターン終了時の自動変換（src/hooks/useGameState.js の turn_end_convert 処理、
  4128行付近と、アクティブバフによる変換）
- スキルによる変換（src/engine/PuzzleEngine.js の convertColor / convertMultiColor /
  convertPairColors / convertAreaToColor / convertStarTargeted /
  convertBombTargeted / convertRepeatTargeted / convertRowNeighbors など）
- 侵食系（erosion_*）など、ターン経過で盤面が書き換わる効果全般

演出の要件：
- 変換されるマスを短く光らせてから（0.15秒程度）、新しいドロップへ
  切り替わるアニメーション（縮小→拡大、フリップなど）にしてください。
- 複数マスが変わるときは、少しずつ時間をずらして順番に変えてください
  （合計0.5秒以内）。
- ターン終了時の自動変換は、どのトークンの効果で変わったかわかるよう、
  トークンアイコンを光らせるか通知を出してください。
- 設定の速度倍率（speedMultiplier）に合わせて演出時間を短縮してください。
- 演出中は盤面操作を受け付けないようにし、演出終了後に操作できるようにしてください。
- 既存の生成演出（プラス・リピートドロップなどの生成時）があれば、
  見た目を揃えてください。

実機（スマホ幅）で違和感がないか、可能なら画面確認してください。
npm test と npm run build が通ることを確認してください。
```
